The agent loop

Eight steps, every one logged.

Not a chatbot bolted onto a dashboard. Every failed payment runs the same observable pipeline, end to end — the same shape as Razorpay's own Agent Studio workflows.

01

Observe

A payment.failed webhook lands and opens a recovery case.

02

Retrieve context

Customer segment, lifetime value, and prior recovery history are pulled in.

03

Predict

An XGBoost model scores recovery probability from real transaction signal.

04

Reason

A deterministic decision engine turns that score into an action, channel, and discount.

05

Select tool

Payment link + notify, delay & retry, escalate to a human, or skip — never free‑form.

06

Execute

A Razorpay payment link is created and a message goes out on the customer's channel.

07

Verify

The outcome is monitored against the follow‑up webhook or a simulated response.

08

Memory

The result is written back to the customer record, shaping the next decision.

Guardrails

The part worth auditing.

The architecture deliberately separates the parts that decide from the parts that talk. What moves money is deterministic, tested code — not a prompt.

Decisions are code, not prompts

The probability‑to‑action logic is plain, unit‑testable Python. The LLM layer only ever chooses the words for a decision the engine already made — it can't trigger a link, a discount, or an escalation.

Human approval above ₹10,000

Any transaction over the threshold is routed to human review before the agent acts — no exceptions, enforced in the decision engine itself.

Discounts capped at 10%

Incentives are only offered on genuinely marginal cases — never on a high‑confidence recovery or an already‑lost one.

Opt‑out enforced in code

Customers who've opted out are never contacted — checked in the decision engine before any tool call, not left to prompt instructions.
